# スポット周辺検索アプリ

地図上で周辺のスポットを検索・閲覧できる Web アプリケーションです。

## 1. 環境構築

### 必要なもの

- Docker / Docker Compose（Docker Desktop, OrbStack 等）
- Git

外部APIキーは不要です。地図タイル（OpenStreetMap）と逆ジオコーディング（Nominatim）はいずれもキー不要のため、環境変数の設定なしで動作します。

### セットアップ

```bash
git clone <リポジトリURL>
cd <リポジトリ名>
```

## 2. 実行手順

```bash
docker compose up
```

初回はイメージのビルドに数分かかります。以下の3サービスが起動します。

| サービス | URL | 役割 |
|---|---|---|
| web | http://localhost:3000 | フロントエンド（Next.js） |
| api | http://localhost:3001 | バックエンドAPI（NestJS） |
| db | localhost:5432 | PostgreSQL + PostGIS |

起動完了後、ブラウザで http://localhost:3000 を開いてください。シードデータ（200件のスポット）はAPI起動時に自動でDBにインポートされます。

### テスト

```bash
# バックエンド単体テスト
cd backend && npm test

# E2Eテスト（コンテナ起動中に実行）
npx playwright install chromium
npx playwright test
```

## 3. 使用した主要ライブラリとその選定理由

### フロントエンド

| ライブラリ | 選定理由 |
|---|---|
| **Next.js (App Router)** | 課題指定。`output: "standalone"` でDockerイメージを軽量化 |
| **Tailwind CSS** | 課題指定。ユーティリティファーストでUIを素早く構築できる |
| **Leaflet + react-leaflet** | APIキー不要で `docker compose up` 一発起動の確実性を最優先した。Google Maps はキー発行＋課金設定が採点環境にも必要になるため除外。MapLibre GL JS はモダンだが無料タイルソースの選定に一手間ある |
| **OpenStreetMap タイル** | Leafletの地図タイルとして採用。キー不要・無料・十分な品質 |

### バックエンド

| ライブラリ | 選定理由 |
|---|---|
| **NestJS** | 課題指定。Module/Controller/Service の構造でコードの見通しが良い |
| **TypeORM** | 課題指定。Entity定義からPostGISのgeography型・空間インデックスを宣言的に扱える |
| **csv-parse** | シードCSVのパース。軽量で型安全なストリーミングパーサ |
| **class-validator / class-transformer** | クエリパラメータのバリデーションと型変換。NestJSのValidationPipeと組み合わせて入力検証を宣言的に行う |

### データベース

| 技術 | 選定理由 |
|---|---|
| **PostgreSQL + PostGIS** | 課題で推奨。geography型は緯度経度をそのまま扱え、距離計算がメートル単位になる。GiSTインデックスにより `ST_DWithin` での半径検索がインデックススキャンで高速に動作する。199件規模では素のlat/lng + Haversine計算でも動くが、データ量が増えた場合のスケーラビリティと、空間データを扱う設計意図を明確にするためPostGISを採用した |

### 逆ジオコーディング

| 技術 | 選定理由 |
|---|---|
| **Nominatim (OpenStreetMap)** | キー不要・無料・日本語対応。当初は国土地理院APIを予定していたが、実装時に403 Forbiddenで利用不可が判明したため変更した。1リクエスト/秒の利用制限があるが、後述のdebounce＋キャッシュで問題なく運用できる |

## 4. 実装時に工夫した点・技術的判断を行った箇所

### docker compose up の確実性

最重要要件として「初期状態から動作可能」を担保するために以下を徹底した。

- **外部APIキーへの依存をゼロにした**: 地図（OSMタイル）も逆ジオ（Nominatim）もキー不要のものを選定。採点者が `.env` を設定する必要がない
- **healthcheck + depends_on condition**: DBが応答可能になってからAPIを起動する起動順制御。これがないと「API起動→DB未準備→接続エラー」が発生する
- **冪等なシーダー**: テーブルにデータがあればインポートをスキップする。コンテナの再起動で二重登録されない
- **マルチステージビルド**: ビルド用の依存（TypeScriptコンパイラ等）を実行用イメージに持ち込まず軽量化

### 逆ジオコーディングのコスト削減（二段構え）

外部APIの呼び出し頻度を抑制するため、フロントとバックエンドの両方で対策を実装した。

1. **フロント側: debounce（400ms）** — 地図をドラッグしている最中はAPIを呼ばず、操作が止まってから問い合わせる
2. **バックエンド側: 座標丸めキャッシュ** — 緯度経度を小数第3位に丸めてキャッシュキーにする（0.001度 ≈ 約100m）。わずかな移動では同じキャッシュキーになるため、APIを叩かずにキャッシュから返す。同一地点への再問い合わせも防ぐ

この設計により、地図操作中のAPI呼び出しは「操作停止後」かつ「約100m以上移動した場合のみ」に限定される。

### データ設計

- **geography型 + GiSTインデックス**: `ST_DWithin` による半径検索はインデックスを利用できるため、データ量が増えてもフルスキャンにならない。距離の単位がメートルになる点も扱いやすい
- **lat/lngカラムの併設**: geography型とは別に素のlat/lng値もカラムとして保持している。API応答やフロントでの座標参照時にgeography型からの変換処理を不要にするため

### フロントエンド

- **地図⇔リストの双方向連動**: リスト選択で地図がflyTo、マーカーのポップアップに距離表示
- **検索範囲の可視化**: 半径をCircleとして地図上に描画し、検索範囲を直感的に把握できるようにした
- **0件時のハンドリング**: 「半径を広げるか、地図を移動してみてください」の案内を表示

## 5. 時間不足で簡略化した箇所・今後の改善点

### 簡略化した箇所

- **DBマイグレーション**: `synchronize: true` でEntity定義からテーブルを自動生成している。実運用ではTypeORMのマイグレーション機能でスキーマ変更を管理する
- **逆ジオコーディングのキャッシュ**: インメモリ（Map）で実装しているため、APIコンテナの再起動でキャッシュが消える。実運用ではRedis等の外部キャッシュに移行する
- **エラーハンドリング**: APIエラー時のリトライ機構は未実装。現状はフォールバックメッセージを表示するのみ

### 今後の改善点

- **検索の絞り込み**: カテゴリ別フィルターや名前検索を追加し、スポットを探しやすくする
- **スポット詳細**: マーカークリック時に詳細情報（説明・画像等）を表示するパネルを追加する
- **モバイル対応**: 現状はPC向けの横並びレイアウト。レスポンシブ対応でモバイルでも使えるようにする
- **CI/CD**: GitHub Actionsでlint・テスト・Dockerビルドを自動実行し、品質を継続的に担保する
